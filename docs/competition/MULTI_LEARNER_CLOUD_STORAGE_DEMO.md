# 云存储技术多学习者个性化 Demo 需求与操作脚本

> 状态：演示需求基线与人工操作脚本
> 主题：云计算 / 云存储技术
> 核心项目：对象存储分片上传、断点续传与幂等恢复
> 演示形式：三个隔离桌面实例、三个学习者、同一个项目
> 说明：本文描述期望演示行为，不等同于声明所有个性化结果已经通过自动化或现场验收。

## 1. 演示目标

本 Demo 用三个学习者完成同一个云存储项目，展示 LearnFlow 如何依据不同学习者的已有知识、实践经验、明确误解、求助行为和作答证据，提供不同的学习路径、辅助等级与纠错策略。

演示要证明的不是“系统给三个人分配了三个不同项目”，而是：

```text
相同课程主题
  + 相同项目目标
  + 相同预期产物
  + 相同关键任务
  + 不同学习者状态与过程证据
  -> 不同的下一步、讲解方式、练习粒度和纠错重点
```

现场核心表述：

> LearnFlow 让三位学习者面对同一个云存储项目，再依据每个人已经掌握的内容、暴露的误解、实践证据和求助行为，选择不同的下一步。个性化发生在学习路径、辅助等级和纠错策略上，而不是简单替换项目标题。

## 2. 控制变量要求

三个学习者必须使用完全相同的：

- 项目类型；
- 项目主题；
- 学习目标；
- 预期产物；
- 初始摸底问题；
- 最终综合挑战；
- 演示时允许使用的工具与模型能力。

三个学习者只允许在以下方面不同：

- 注册时填写的教育阶段与学习背景；
- 关注方向、每周学习时间和偏好方式；
- 对摸底问题的回答；
- 是否主动求助以及选择哪种辅助；
- 后续练习结果和由此形成的证据。

每个桌面实例使用独立账号和独立本地数据。项目的数据库 ID、会话 ID 可以不同，但面向学习者的项目字段必须逐字一致。

## 3. 演示范围

### 3.1 本次必须展示

1. 三个隔离桌面实例可同时运行。
2. 三个账号分别登录，各自只看到自己的项目和学习状态。
3. 三个账号建立内容完全相同的云存储项目。
4. 三人收到相同摸底问题，但给出不同回答。
5. Tutor 根据回答给出不同下一步。
6. 至少展示一次“换种讲法、看步骤或看示例”的主动求助。
7. 至少展示一次针对明确误解的纠错，而不是泛化重讲。
8. 三人接受相同最终挑战时，获得不同粒度的支架与反馈重点。
9. 展示项目进度、学习路径或学习者画像相互隔离。

### 3.2 本次不要求展示

- 不要求使用 Role Atlas。岗位目标会引入额外变量，不利于本轮控制变量对比。
- 不要求三个账号协作编辑同一份项目数据。
- 不要求证明真实教学增益或长期掌握，只展示产品中的可检查差异与证据链。
- 不把模型生成内容、普通对话或一次答对直接宣称为稳定掌握。
- 不把代码运行成功直接视为学习证据；只有正式提交、判定和登记事件才能进入学习证据链。

## 6. 创建完全相同的项目

三个窗口均选择“做一个作品或实验”，并逐字输入以下内容。

### 6.1 项目主题

```text
对象存储分片上传：断点续传与幂等恢复实验
```

### 6.2 学习目标

```text
理解对象存储中 Bucket、Object、Key、Upload ID、Part Number 和 ETag 的作用；掌握分片上传失败后的状态恢复、失败分片重试和完成请求幂等处理；能够独立设计并验证一个支持程序重启、网络中断和重复请求的可靠上传流程。
```

### 6.3 预期产物

```text
一个可运行的分片上传原型、一份异常恢复测试记录、一张上传状态机图，以及一份幂等与一致性设计说明。
```

输入完成后，分别点击“建立项目工作台”。创建完成后，先并排展示三个项目页面，确认项目主题、学习目标和预期产物完全一致。

讲解词：

> 三位学习者看到的是同一个课程项目。每个账号拥有自己的隔离副本，因此不会互相污染学习记录，但任务内容和验收标准完全一致。

## 7. 共同摸底问题

进入各自项目 Tutor 后，三个窗口发送完全相同的消息：

```text
我要完成这个云存储项目。请先不要直接给出实现方案，只根据下面三个问题判断我的当前基础：

1. 对象存储与传统文件存储的主要区别是什么？
2. 一个 1GB 文件被分成多个分片上传，第三个分片失败后应该怎样恢复？
3. 怎样保证分片重试和完成上传请求被重复发送时不会产生错误结果？

请在我回答后再安排下一步，并说明为什么这样安排。
```

操作要求：等待每个窗口的 Tutor 完整回应后，再输入对应学习者的回答。不要同时快速提交多轮消息，以免影响现场观察。

## 8. 学习者 1 对话脚本

### 8.1 摸底回答

```text
1. 我觉得对象存储就是把文件放到云端，和网盘或者普通文件夹应该差不多。
2. 如果第三个分片失败，我猜需要把整个文件重新上传。
3. 我不太理解幂等。我觉得给每个分片换一个新名字，应该就不会重复了。

我对 Bucket、Key、Upload ID 和 ETag 都不熟悉。
```

观察点：Tutor 应识别基础缺口，不应立即要求学习者独立完成完整上传器。

### 8.2 主动请求换讲法

如界面提供“换种讲法”，先点击该入口，再发送：

```text
我还是分不清 Bucket、Object 和 Key。请换一种讲法，用“仓库、货架和包裹”的类比解释，并画出它们之间的关系。先不要进入代码。
```

观察点：新讲法应响应当前明确请求；旧讲法无效及新讲法选择应形成可检查的用户级证据，而不只是替换界面文字。

### 8.3 理解复述

```text
我的新理解是：

- Bucket 像一个独立仓库；
- Object 是实际保存的对象；
- Key 是对象在 Bucket 中的唯一标识；
- Upload ID 标识一次分片上传会话；
- Part Number 标识分片的位置；
- ETag 可以帮助服务端确认已经接收的分片。

请检查这段理解，并只给我一个 15 分钟以内的下一步练习。
```

### 8.4 小练习回答

```text
我会先保存 Upload ID，再记录每个已经成功上传的 Part Number 和 ETag。程序重启后先查询服务端已经存在的分片，只重新上传缺失的分片。
```

本窗口预期结论：Tutor 采用概念补偿、类比、小步练习和较高辅助等级。

## 9. 学习者 2 对话脚本

### 9.1 摸底回答

```text
1. 对象存储通过 Bucket 和 Key 管理对象，不提供传统文件系统那样的目录与随机块修改语义。
2. 分片上传失败后，应保留 Upload ID 和已经成功的分片，只重试失败或缺失的分片。
3. 我认为可以使用 Upload ID 加 Part Number 标识一次分片写入，并在完成上传前校验服务端分片列表。

这些概念我基本理解，但没有实现过状态持久化、程序重启恢复和故障注入测试。
```

观察点：Tutor 应跳过大段对象存储基础讲解，直接聚焦工程实践缺口。

### 9.2 请求设计任务

```text
请不要重复解释对象存储基础。让我先设计上传状态表，并指出必须覆盖的异常场景。暂时不要给出完整实现。
```

### 9.3 提交状态设计

```text
我准备保存这些字段：

- object_key
- upload_id
- part_number
- etag
- local_file_hash
- upload_status
- retry_count
- updated_at

恢复时读取本地状态，再调用服务端 ListParts 对账，以服务端已经确认的分片为准。

我准备验证：

1. 单个分片上传超时；
2. 分片成功但客户端没收到响应；
3. 程序上传一半后退出；
4. 同一分片重复上传；
5. Complete 请求被重复发送。
```

### 9.4 请求审查而非代做

```text
请审查这个设计，找出最危险的两个遗漏，然后给我一个最小接口骨架和验收测试清单，但不要代替我完成代码。
```

本窗口预期结论：Tutor 直接进入状态模型、工程产物和故障测试，采用中等辅助等级。

## 10. 学习者 3 对话脚本

### 10.1 含明确误解的摸底回答

```text
1. 对象存储以 Key 访问对象，我已经使用过 S3 兼容接口。
2. 分片失败后可以根据 Upload ID 继续上传。
3. 我认为 ETag 永远就是文件内容的 MD5；只要分片内容相同，重试时使用不同的 Part Number 也没有关系。CompleteMultipartUpload 如果超时，直接重复发送同一个请求即可。

请优先检查我的边界条件，不需要再讲基础概念。
```

这里故意暴露两个关键误解：

- ETag 不能在所有对象存储实现和所有上传方式下无条件等同于普通文件 MD5；
- Part Number 参与分片标识和最终合并顺序，重试时不能随意改变。

观察点：Tutor 应针对明确误解进行纠错，不应把学习者当作新手重讲整门课程。

### 10.2 请求反例，不提前索取答案

```text
请先不要告诉我答案。给我一个能够检验以下两个判断的反例场景：

1. ETag 一定等于对象内容的 MD5；
2. 同一分片重试时改变 Part Number 不影响最终对象。

让我先预测结果。
```

### 10.3 故意作出错误预测

```text
我的预测是：最终对象内容不会变化，因为服务端可以根据分片内容识别重复数据；最终 ETag 仍然等于完整文件的 MD5。
```

### 10.4 修正后的结论与迁移任务

```text
我修正后的结论是：

- 不能把 ETag 无条件当作对象内容的 MD5；
- Part Number 同时参与分片标识和最终合并顺序；
- 恢复时必须使用 Upload ID 查询服务端实际接收的分片；
- Complete 请求是否可以安全重放，要依据服务端契约和当前上传状态判断。

请给我一个包含“响应丢失、程序重启、重复 Complete 请求”的故障注入测试，让我独立写出预期状态变化。
```

### 10.5 最终回答

```text
我会分别记录客户端状态和服务端状态。Complete 请求超时后不立即假定失败，也不直接创建新的上传会话；先查询对象或上传会话状态，再根据服务端结果决定重试、结束或人工处理。
```

本窗口预期结论：Tutor 不重复基础内容，而是通过反例、预测、纠错和故障注入处理边界误解。

## 11. 三人共同最终挑战

完成各自前序对话后，给三个人发送完全相同的综合任务：

```text
现在进行同一个最终挑战：

一个 1GB 文件被切分为 5 个分片。第 3 个分片上传成功后响应丢失，随后程序崩溃。程序重启后，用户再次点击上传，并且 Complete 请求也可能被重复发送。

请给出：

1. 必须持久化的状态；
2. 重启后的恢复顺序；
3. 分片级幂等键；
4. Complete 请求的处理原则；
5. 至少 4 个验证用例。

请根据我的当前学习状态决定是否提供提示。
```

预期对比：

| 学习者 | 合理的差异化支持 |
|---|---|
| 学习者 1 | 提供状态图、字段模板、步骤拆解和概念提醒 |
| 学习者 2 | 直接要求完成接口与测试设计，只提示遗漏和风险 |
| 学习者 3 | 聚焦 ETag、Part Number、响应丢失和 Complete 重放边界 |

这些结果必须来自当前账号的有 scope 学习者投影和过程证据，不能通过在三个项目中预写不同提示词来伪造个性化。

## 12. 现场演示顺序与讲解词

建议使用 8—12 分钟完整版本。

### 12.1 开场：控制变量（约 45 秒）

操作：并排展示三个窗口的项目页。

讲解词：

> 这是三位不同学习者，但他们创建的是完全相同的云存储项目。我们固定课程、目标、产物和最终挑战，只改变学习者背景与学习过程，从而观察系统是否真正依据学习状态进行适配。

### 12.2 展示学习者差异（约 45 秒）

操作：依次展示三个账号的背景摘要。

讲解词：

> 第一位学习者缺少对象存储基础；第二位理解概念但没有工程实践；第三位有开发经验，却对 ETag 和幂等边界存在明确误解。系统不能只按“新手、高级”贴标签，而要根据具体证据决定下一步。

### 12.3 相同摸底、不同作答（约 90 秒）

操作：展示相同摸底问题，再依次展示三份回答。

讲解词：

> 三个人面对同样的问题。差异不是由项目标题触发，而是由他们真实暴露的知识、实践和误解触发。

### 12.4 对比三个下一步（约 2 分钟）

操作：

1. 学习者 1 展示类比和小步练习；
2. 学习者 2 展示状态表与故障测试；
3. 学习者 3 展示反例与边界纠错。

讲解词：

> 同一个云存储目标被分解成了三个不同的当前动作：补概念、做工程设计、纠正高风险误解。系统改变的是到达同一目标的路径，而不是降低或替换最终标准。

### 12.5 展示主动求助证据（约 60 秒）

操作：在学习者 1 窗口点击“换种讲法”或发送对应请求。

讲解词：

> 这里的“换种讲法”不是一次性 UI 切换。无效讲法和学习者选择的新支持方式应成为可检查证据，影响后续辅助，但不能仅凭一次选择推断固定学习风格。

### 12.6 相同最终挑战（约 2 分钟）

操作：三个窗口发送相同最终挑战，展示支架差异。

讲解词：

> 最终任务和验收标准仍然一致。学习者 1 获得更多结构化支架，学习者 2 直接进入接口与测试设计，学习者 3 被重点追问最容易造成生产事故的边界。

### 12.7 证据与隔离（约 60 秒）

操作：打开每个账号的学习路径、项目进度、学习者画像、纠错记录或证据详情中现场可用的页面。

讲解词：

> 三个账号的记录彼此隔离。系统保存的是有来源、有作用域的学习证据；模型可以生成讲解候选，但不能直接宣布掌握，也不能直接修改五核状态。

### 12.8 收束（约 30 秒）

讲解词：

> LearnFlow 的个性化不是给每个人换一套内容，而是在同一个真实项目中持续回答三个问题：他现在缺什么、下一步最合适做什么、什么证据足以证明他真的会了。

## 13. 3—5 分钟压缩版

时间不足时，只展示：

1. 三个完全相同的项目页；
2. 三份不同的摸底回答；
3. 三个不同下一步；
4. 学习者 1 的“换种讲法”；
5. 三人相同最终挑战的不同支架；
6. 三个账号的状态隔离。

压缩版不要现场从头等待所有模型调用，可提前完成前序对话并停在关键结果页面，但必须保留可追溯的真实历史，不能使用静态截图冒充运行结果。

## 14. 验收标准

### 14.1 环境验收

- [ ] 三个桌面窗口标题清晰可区分。
- [ ] 三个窗口可同时打开、登录和发送请求。
- [ ] 三个实例的健康检查正常。
- [ ] 学习者 2、3 注册与登录不再出现来源校验失败。
- [ ] 每个实例使用独立数据目录和账号。

### 14.2 项目一致性验收

- [ ] 三个项目类型都为“做一个作品或实验”。
- [ ] 三个项目主题逐字一致。
- [ ] 三个学习目标逐字一致。
- [ ] 三个预期产物逐字一致。
- [ ] 三个项目的最终验收标准一致。

### 14.3 个性化行为验收

- [ ] 新手不会被直接推入完整工程实现。
- [ ] 理论型学习者不会被迫重复已明确掌握的基础概念。
- [ ] 有经验学习者的 ETag 与 Part Number 误解被明确识别并纠正。
- [ ] 三个账号收到不同的下一步或不同粒度支架。
- [ ] “换种讲法、看步骤或看示例”的选择可检查。
- [ ] 一次正确复述不会被宣称为稳定掌握。
- [ ] 有提示成功与独立成功能够区分。
- [ ] 相同最终挑战不会因为账号切换而串用其他学习者历史。

### 14.4 证据与安全验收

- [ ] 重要学习行为通过登记事件进入统一证据链。
- [ ] learner、project、checkpoint、session 作用域正确。
- [ ] 普通对话或生成内容不会直接修改掌握状态。
- [ ] 重复提交不会重复计分或重复写入同一证据。
- [ ] 演示材料不包含秘密、真实账号凭据或原始私有数据。

## 16. 故障预案

### 16.1 某个桌面窗口无法请求

1. 确认对应前端端口可访问；
2. 确认对应 sidecar 健康检查返回成功；
3. 确认前端代理指向当前 sidecar 端口；
4. 检查前端来源是否在 sidecar 的 CORS allow-list 中；
5. 重启该实例后再次检查，不复用其他学习者数据库。

### 16.2 模型不可用或响应不稳定

- 已完成的真实对话历史可作为压缩版演示材料；
- 明确说明模型只负责候选讲解和表达，确定性判定与证据链不应依赖模型；
- 如果当前多学习者场景尚未 seeded，不得声称该场景已经离线确定性验收。

### 16.3 三个结果没有明显差异

- 先确认三个账号的背景和回答确实分别保存；
- 检查是否误在同一账号或同一数据库中演示；
- 检查 Tutor 是否读取了当前 learner/project 的状态投影；
- 将实际结果记录为待修复缺口，不修改共同项目字段来规避问题。

### 16.4 状态串号

立即停止演示并重新建立隔离实例。账号间状态泄漏属于演示阻断问题，不能继续作为个性化证据展示。

## 17. 后续产品化要求

当前脚本可用于人工创建与现场演示。若要形成可重复的正式比赛 Demo，还应继续实现：

1. 三个隔离学习者的固定 seed；
2. 同一云存储项目的固定 seed；
3. 三套可重放的历史证据与确定性当前状态；
4. 一键登录或明确的演示账号切换入口；
5. 三学习者对比视图或演示导航；
6. 不依赖外部网络和 LLM 的核心闭环；
7. 用户隔离、幂等、事件顺序和证据等级回归测试；
8. 每次运行使用隔离演示数据库，并提供安全重置流程。

实现上述内容时，必须保持以下架构边界：

```text
用户 / UI / Tool / Agent 行为
  -> EvidenceEvent
  -> five_kernel_reducer
  -> KernelMutation
  -> KernelState
  -> MemoryFact -> MemoryModule -> MemoryClaim
```

Tutor、学习设计能力、实践能力、UI、工具或 LLM 均不得绕过统一事件入口直接修改五核状态。
