## 统一循环，而非统一答案

实验工作台采用下面的循环。它是我们的产品设计，不是任何一个课程的原文规范。

1. **读懂任务。** 要交什么？输入输出是什么？不可改变哪些接口？如何判断最小成功？
2. **留下预测。** 修改前预期什么结果？根据哪条机制？用一个最小输入手算。
3. **做最小实验。** 先得到可复现基线，再改变一个变量；选定真实文件版本运行。
4. **解释差异。** 预期与观察哪里不同？证据指向哪个假设？下一次如何排除其他原因？
5. **独立迁移。** 换一个边界输入或限制条件；样例通过不能直接宣称掌握。
6. **自选探索。** 基础正确后再比较性能、空间、可维护性或不同设计；每个想法留下可测预测。

以 SAT/C 项目为例，可以问“空子句与空子句集的结果是否相同”“单位传播的哪一步改变了当前状态”“一个已知可满足实例改变一条约束后，你预期会发生什么”。这些只是我们的示例提问，不是对用户代码已验证的结论，也没有执行用户的工程。

## 三类项目怎样用同一循环

| 类型 | 主要输入 | 导师引导 | 用户保留的记录 |
| --- | --- | --- | --- |
| 学习型 | 书籍、课程、讲义的固定版本 | 带问题阅读 → 脱离资料复述 → 独立应用 → 复习 | 来源与位置、问题纸、复述、正式练习和复习记录 |
| 实验型 | 任务书、真实工程与工具链 | 明确产物 → 预测 → 分步实现 → 运行验证 → 交付与下一步实验 | 文件版本、真实输出、假设纸、复现方式和产物引用 |
| 实践型 | 有来源等级的版本化工作案例 | 接手背景 → 澄清约束 → 有限提示 → 阶段交付 → 新情况 → 交接复盘 | 当前材料、判断依据、帮助程度、反馈和交付物 |

提示按需要逐步加深：先问值得验证的问题；学生卡住时指向一个文件、接口或约束；仍困难时一起分解一个局部步骤。看到示范后的完成不能记成独立完成。当前案例实现了两档提示与帮助程度记录；自动判断学生需要哪一档、自动生成变式仍需后续教学评估。

## 本轮已落实的位置

- 三种任务书共用正式 Project/Roadmap/Checkpoint/LearningTask/Session，没有再建立一套学习状态。
- 实验默认阶段包含预测、观察、解释、复现与下一步实验；假设纸保留问题与想法。
- 普通文件引用包含路径、版本和选区；编译、运行、可见用例比较返回真实结果。
- 实践案例固定版本和 hash，先备交付通过才开放后续材料；提示和交付不直接产生掌握结论。
- 学习阶段保留来源版本与阅读位置，最终阶段引用正式独立验证及复习记录。
- 导师读取当前流程的有界投影：不注入全部纸张，不泄漏未来材料或 evaluator。

具体启动与能力边界见[三类项目的本地工作台](../implementation/LOCAL_PROJECT_WORKBENCH.md)。下一步内容建设应先做少量可验证实验模板，再逐步形成覆盖编程、数据结构、系统、网络与软件工程的课程实践目录。
