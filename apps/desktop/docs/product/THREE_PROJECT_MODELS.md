# LearnFlow 三类学习项目产品规格

状态：产品方向已确认，实施规格草案

日期：2026-09-05

适用范围：LearnFlow Web 与 Desktop 项目工作台

配套上线设计：[产品上线部署与数据归属](../implementation/PRODUCT_DEPLOYMENT_AND_DATA_OWNERSHIP.md)。

> 本文确认产品方向，不表示文中“建议”与“待实现”能力已经存在。判断当前能力时，以
> `backend/app/services/architecture_registry.py`、`docs/ARCHITECTURE_AUTHORITY.md`、
> `docs/AGENT_ARCHITECTURE_GUIDE.md` 和运行实现为准。

## 1. 定位

LearnFlow 的项目不是课程文件夹，也不是通用 IDE 外壳，而是围绕一个可检查目标持续学习、实践、验证和复盘的
Tutor 工作空间。同一套 Project 结构支持三种主要起点：

1. **学习型项目**：从书、课程、讲义或一组可信资料出发，目标是系统理解并能应用。
2. **实验型项目**：从本地软件工程、实验要求和目标交付物出发，目标是在真实文件与工具中做出来。
3. **实践型项目**：从经核验的真实工作任务或教学案例出发，目标是在有角色、环境、约束和评价的情境中完成一次类实习实践。

三类项目使用相同的对象、Tutor 和证据链，只改变项目如何建立、工作区默认突出什么，以及每关怎样组织学习材料与实践。
项目类型不是三套互不兼容的产品，也不能产生三套学习者状态。

## 2. 共同产品骨架

### 2.1 保留现有正式对象

**当前：**正式项目沿用下面的关系，不另建浏览器本地项目权威：

```text
Project
  └─ Roadmap（可版本化的关卡 DAG）
       └─ Checkpoint
            ├─ 固定作用域的 Tutor Session
            └─ 唯一 LearningTask
                 └─ 多个内部 work_steps / 教学阶段 / 产物引用
```

- `Project` 保存持续目标、预期真实产物、来源集合和本地工作区绑定。
- `Roadmap` 保存依赖、顺序与修订版本；进入学习的节点锁定，未开始节点可经提案和确认后修订。
- `Checkpoint` 是学习者看得见、可返回、可验收的阶段里程碑。
- 一个 Checkpoint 对应一个正式 `LearningTask`；细小操作保存在任务内部 `work_steps`，不把“读一段、改一行、运行一次”都升级成关卡。
- 项目 Tutor 负责长期规划与跨关协调；关卡 Tutor 负责本关带领；项目自由对话负责不自动推进路线的探索。它们都是
  `tutor_agent` 的不同 scope。

现有合同参见 `docs/ARCHITECTURE_AUTHORITY.md` 的“vNext 项目学徒旅程”、
`docs/AGENT_ARCHITECTURE_GUIDE.md` 的“vNext 项目 Tutor、关卡与项目自由对话”，以及
`backend/app/models/project.py`、`backend/app/models/learning.py`。

### 2.2 四种内容权威

| 内容 | 权威位置 | 在界面中的表现 | 边界 |
| --- | --- | --- | --- |
| 普通项目文件 | 用户本地磁盘 | 文件树、编辑器、diff、外部工具入口 | LearnFlow 不复制一份影子工程；修改必须有版本检查与可审计操作 |
| 来源与受管学习对象 | 数据库中的 `Source/SourceVersion/Chunk`、`Lecture/Exercise` 等 | 来源阅读器、讲义纸、练习纸 | 来源是有 provenance 的上下文；练习答案保持隔离 |
| 纸张 | 会话内的 `PaperSheet` 引用、父子关系和分支消息 | 主纸、材料纸、代码选区纸、结果纸、想法纸 | 纸张不复制文件正文，不成为文件、对话或学习状态权威 |
| 学习证据 | `LearningAttempt -> EvidenceEvent -> reducer` | 判题结果、纠错、迁移与复习 | 生成、阅读、运行成功、保存文件和任务完成均不能直接代表掌握 |

**建议：**任何可在纸张中打开的对象都使用类型化引用，例如受管文件 ID、本地文件相对路径 + 内容 hash、代码选区
`path + revision + line range`、某次工具运行 ID 或工作案例对象 ID。打开时从原权威读取；引用失效时显示版本变化并允许用户
定位新版本，不能静默展示旧正文冒充当前文件。

**当前持久化边界：**正式 `AgentSession/AgentMessage` 及其主对话是后端权威；纸张的部分元数据、父子/分支投影、布局和标签页
工作区仍保存在浏览器缓存（`localStorage`）中。同一设备刷新时可以恢复部分现场，但这不是跨设备权威，也不能替代正式
Session/Message。跨设备持久化纸张树、分支元数据和工作区布局仍待实现；后续应以学习者与 Session 为作用域保存纸张投影，继续
引用正式消息、文件和受管对象，而不是复制一套新的消息或文件正文。

### 2.3 持续 Tutor 与教学节奏

每个关卡采用同一条可解释的支持梯度：

```text
建立目标与成功标准
  → Tutor 在等价小例子上示范
  → 学生在目标任务上动手，Tutor 只给必要支架
  → 学生独立完成无提示验证
  → 依据正式结果纠错、迁移与复习
```

- **示范**应使用缩小版、同构例子或非计分片段，不能直接泄漏当前考核产物的完整实现。
- **陪做**允许逐步提示、选区解释、比较方案和检查中间产物；每次提示记录辅助等级。
- **独立验证**必须使用答案安全、可判定的输入和服务端拥有的规则。Tutor 或生成模型不能自行宣布通过。
- 学生可以随时追问和改换讲法；这不自动推进任务步骤，也不自动改变长期偏好或掌握状态。

### 2.4 想法、问题与创新

项目不能只有路线执行。任何关卡都可以新建想法纸或使用项目自由对话，记录假设、替代方案、观察、失败原因和希望尝试的
扩展。探索默认不改变 Roadmap。只有当学习者决定继续，项目 Tutor 才形成以下一种待确认提案：

- 本关内部新的 `work_step`；
- 尚未开始的 Checkpoint 修订；
- 新的挑战 Checkpoint；
- 一个独立项目提案。

想法的数量、表达流畅度或模型评价不是创新能力证据。只有真实产物、实验对照、独立解释或迁移验证才能进入正式证据链。

### 2.5 创建与继续入口

创建项目时先让用户选择符合日常意图的入口，而不是要求理解内部枚举：

- **“跟着一本书或一门课系统学习”**：进入资料驱动的来源选择与目标澄清。
- **“在本地工程里完成一个实验或作品”**：进入目录、实验要求、工具与交付物绑定。
- **“把真实工作案例变成一次实践”**：进入案例来源、角色、授权、真实性与阶段约束检查。

三个入口共用同一提案流程：Tutor 根据自然语言和已选对象形成 `LearningProjectProposal`，用户查看目标、Roadmap、交付物与评价后
确认创建。入口只决定默认简报和布局，不创建三套 Project API。

项目首页提供 **“继续昨日工作”**：一次恢复项目模式的界面投影、当前 Checkpoint/LearningTask、原 Tutor Session、活动纸张/分支、
文件标签页以及上次记录的文件版本。恢复本地工程时重新校验绑定目录、内容 hash 与磁盘当前版本；发生漂移就展示差异和选择，不能
静默覆盖。当前 Project/Task/Session 已有稳定锚点，但纸张、布局和文件标签的跨设备整体恢复属于待实现能力。

## 3. 三类项目对照

| 维度 | 学习型：资料驱动 | 实验型：本地交付物驱动 | 实践型：工作案例驱动 |
| --- | --- | --- | --- |
| 首要输入 | 书、课程、讲义、标准或版本化资料 | 本地工程、实验要求、已有代码、构建与验收约束 | 经核验工作案例、岗位任务、工作区事件与交付证据 |
| 项目目标 | 建立结构化理解并能解题、解释和迁移 | 在自己的目录中完成可运行、可检查的软件或实验产物 | 在角色与情境约束下完成一次可评价的工作闭环 |
| 默认中心视图 | 材料纸与学习路线 | 文件树、编辑器和工具输出 | 案例任务台、阶段事件、交付物与反馈 |
| Roadmap 依据 | 内容结构、先备知识、练习与复习节奏 | 工程依赖、实验阶段、接口与交付门 | 案例阶段、信息披露、决策点、交付与评价门 |
| 典型纸张 | 原文、概念追问、例题、错题、总结 | 代码选区、设计草图、运行结果、调试假设、实验报告 | 情境简报、消息/工单、证据、决策记录、交付物、复盘 |
| 正式验证 | 题目、讲解复述、变式迁移 | 编译/测试 + 产物验收 + 独立解释 | 隐藏标准、案例 rubric、结果证据、情境迁移 |
| 本地文件是否核心 | 可选 | 必需 | 按案例而定，软件类实践通常必需 |

项目可在演进中吸收另一类能力。例如一本操作系统教材可在后半段增加本地实验；SAT 实验可引用课程材料；真实工作案例可先
安排知识补齐。项目的主类型决定默认体验，不禁止组合。

## 4. 学习型项目：资料驱动的系统学习

### 4.1 端到端流程

1. 学习者选择书、课程或资料集，说明目标、现有基础、时间与预期产出。
2. 系统处理来源、固定版本并显示覆盖、冲突、缺口和可信度；学习者确认项目来源基线。
3. 项目 Tutor 提出 Roadmap：每关绑定明确章节/主题、先备知识、产物与成功标准，学习者确认后物化。
4. 进入关卡时，中心区域打开当前材料锚点；Tutor 只给本轮阅读目标和一个检查问题。
5. 学习者可以对原文、公式、图、代码或 Tutor 解释开子纸；分支消息保留祖先上下文。
6. 关卡内经过示范、练习和独立验证；错题进入纠错与后续变式，而不是用“看完章节”标记掌握。
7. 关卡结束后保存返回位置、未解决问题、正式 Attempt 与到期复习；跨章节路线只由确认后的结构事件更新。

### 4.2 功能规格

**当前可复用：**项目来源、来源基线、Roadmap/Checkpoint、项目与关卡 Session、讲义/练习文件、纸张引用、LearningTask 和正式
Attempt 链。相关入口见 `frontend/src/ProjectContextPanel.tsx`、`frontend/src/LectureFilePage.tsx`、
`frontend/src/PracticeFilePage.tsx`、`frontend/src/paper-workbench.ts`。

**建议：**

- 书/课程目录解析为待确认结构，不直接成为掌握图；章节与 Checkpoint 可以多对多映射。
- 阅读锚点记录来源版本、段落定位和必要上下文；换版时提示漂移。
- 讲义以来源为边界生成，明确哪些内容来自原资料、哪些是教学改写、哪些尚缺依据。
- 练习覆盖概念识别、解释、计算/编码、真实应用和迁移；帮助后的成功与独立成功分开。
- 支持学习者自己的注释和总结纸，但模型生成摘要不能替代学生的理解证据。

**待实现重点：**更稳定的 EPUB/PDF/课程目录锚点、跨版本定位、书内搜索与笔记导出；这些能力不能通过把整本书正文复制进
浏览器状态实现。

## 5. 实验型项目：本地工程中的交付与发现

### 5.1 端到端流程

1. 学习者创建实验项目或把现有项目切换到实验布局，选择一个可信本地目录。
2. LearnFlow 只读扫描目录、实验任务书、构建入口和当前状态，生成项目简报；绑定目录前展示范围并由用户确认。
3. 项目 Tutor 结合实验要求与现状提出 Roadmap。每关对应一个可验收功能或阶段，一个关卡任务内部可以包含理解接口、修改多个
   文件、运行检查、解释结果和提交证据等多个步骤。
4. 进入关卡后，左侧显示本关相关文件与全部文件；中心保留文件标签、编辑器和下方工具输出；Tutor 固定读取本关 scope。
5. 学习者按原有开发习惯编辑与保存，用选区、错误输出或 diff 开纸张提问。Tutor 可以先启发思路、展示同构小例子，再提出修改
   建议；任何 Agent 修改先显示 diff，确认后才写回。
6. 构建、语法检查、测试或领域工具通过登记过的 Tool Profile 执行，保留命令、输入、环境摘要、输出和退出状态。
7. 工具成功只说明一次运行结果。关卡通过还需满足正式验收规则，并在需要时要求学生解释、修复变式或重新独立完成。
8. 最终交付聚合源码、报告、测试、运行记录和演示清单；删除 LearnFlow 项目不能删除绑定的本地目录。

### 5.2 文件、纸张与外部工具习惯

实验工作台应尊重学生已经形成的电脑使用习惯：

- 文件树使用真实相对路径，支持标签页、脏状态、`Ctrl/Cmd+S`、外部变化提醒和重新读取。
- 学生可以继续用自己的 IDE、Git 和终端；LearnFlow 重新获得焦点时检测 hash 变化，不把外部改动判为冲突或失败。
- 纸张用于讨论一个选区、一次运行、一个设计决定或一个实验假设。关闭纸张不关闭文件，删除纸张不删除磁盘内容。
- 工具面只呈现允许的构建、检查和测试动作；不提供无边界的任意 Shell。工具输出可开结果纸或发送给 Tutor 解释。
- Agent 修改必须先生成 `WorkspaceOperation` 和 diff；基础 hash 变化时停止应用并让学生处理，不能覆盖新内容。
- 练习需要提交多文件产物时，提交的是版本化 manifest 与必要内容/哈希，不把前端页面里的多个临时 textarea 冒充正式提交。

**当前：**后端已有桌面项目目录绑定和可审计 `WorkspaceOperation`，普通文件以磁盘为权威，见
`backend/app/models/project.py` 和 `docs/ARCHITECTURE_AUTHORITY.md` 的“桌面文件工作台”。当前普通文件只支持查看和轻量文本编辑，
架构权威明确尚无编译、解释器、终端或运行入口。`frontend/src/CodePaperWorkbench.tsx` 仍是正式 Exercise 的单段代码提交 UI；其
多文件编辑只停留在页面草稿，不能作为实验工作台实现。

**待实现：**通用实验布局、本关相关文件计算、可靠的多文件提交、登记式构建/检查 Profile、工具运行记录纸、外部编辑同步，以及
把正式运行结果交给 Practice Agent 的确定性适配器。

### 5.3 SAT Studio 参考边界

2026-09-05 只读考察的外部参考：`/Users/a1-6/Downloads/程序设计/sat-studio/`。它不是本仓代码，也不是当前 LearnFlow 可用实现。
可借鉴的产品逻辑包括：阶段/关卡地图、本关任务书、相关文件与全部文件、真实磁盘编辑、精确选区提问、分档提示、Agent diff
确认、构建输出回灌、恢复点与撤销。其 README 同时明确“文件存在、编译成功、自评完成”是不同事实，这与 LearnFlow 的证据边界
一致。

LearnFlow 不应复制一个 SAT 专用页面，而应把上述交互变成可由项目简报和 Tool Profile 配置的通用实验工作台。

## 6. 实践型项目：经核验工作案例中的类实习

### 6.1 工作案例是最小实践单位

实践型项目的最小输入不是一串生成步骤，而是一份有版本、有来源、可复核的 **Work Case Package**。一个工作案例至少包含初始
环境、角色、约束、交付物、评价规则和按阶段可见的信息。它可以来自脱敏真实工作记录、公开案例、受控实验或明确标记的教学
模拟；“真实”与“适合教学”分别判断。

小型案例可确认后转成既有项目中的一个 Checkpoint/LearningTask。跨多个阶段、产物或能力域的案例先形成
`LearningProjectProposal`，由用户确认后物化为 Project、Roadmap、每关唯一 LearningTask。插件不能直接创建第二套项目。

### 6.2 Work Case Package 建议字段

| 字段组 | 必需内容 |
| --- | --- |
| 身份与版本 | `caseId`、schema version、内容 hash、标题、领域、状态、更新时间 |
| 来源与真实性 | 来源对象、定位、许可证/授权、真实性等级、脱敏记录、证据限制、审阅状态 |
| 角色合同 | 学习者角色、责任、允许动作、协作角色、升级路径、不能做的决定 |
| 初始环境 | 可用仓库/数据/服务/工具、初始版本、可复现启动方式、已知状态和资源限制 |
| 目标与约束 | 业务目标、交付期限、质量、安全、隐私、成本和技术限制 |
| 阶段图 | 稳定阶段 ID、依赖、进入条件、完成条件、失败/重试语义 |
| 分阶段信息 | 初始可见材料、触发后出现的消息/日志/需求变化、角色可见范围、披露理由 |
| 工作对象与事件 | 工单、代码、文档、数据、告警、会议或评审事件及其版本引用 |
| 交付物 | 每阶段产物、格式、保存位置、必要证据和最终提交清单 |
| 评价 | 可见成功标准、隐藏验证、rubric、独立验证方式、迁移任务、评价 owner |
| 教学支架 | 可公开先备知识、同构示范、分级提示、停止条件、可用讲法 |
| 解法隔离 | 参考解、关键决策、后续事件和测试秘密的 evaluator-only 引用及 hash |
| 学习映射 | 候选知识/技能/能力目标、先备假设、允许写入的 EvidenceEvent 提案 |
| 返回与恢复 | 项目、关卡、Session、纸张、文件和工具运行的稳定锚点 |

开放式工作交付物应以 rubric、可核对的过程/结果证据和必要的人工评审共同判断质量；编译、测试或 schema 校验只覆盖其中可确定的
部分，不能把所有岗位成果都当作可由代码自动判分的对象。

### 6.3 避免未来解法与事件泄漏

案例包必须把内容分成三层，而不是只靠提示词要求模型“别剧透”：

1. **learner-visible**：当前角色在当前阶段本来就能看到的信息。
2. **mentor-scaffold**：在请求帮助且满足支架规则后可逐级释放的提示、同构示例或背景知识。
3. **evaluator-only**：参考解、隐藏测试、评分细则、后续事件和关键决策，仅供确定性评估或受限工具读取。

阶段解锁由确定性状态机根据显式提交、工具结果或确认事件推进。模型只接收当前可见投影，不能拿到整个案例再被要求自行遗忘。
刷新、切换纸张或恢复 Session 后可见范围必须一致。任何提前披露都记录为辅助，后续成功不得冒充独立完成。

### 6.4 端到端流程

1. 学习者从当前项目、岗位包、公开工作案例或明确授权的工作对象中选择一个候选任务。
2. 插件或外部流程形成 Work Case Package / `LearningProjectProposal` 候选，并附来源、真实性、覆盖、假设与警告。
3. LearnFlow Host 校验 schema、hash、ownership、来源引用、内容分层、阶段 DAG、工具政策与评价可执行性。
4. Tutor 解释角色、环境、预期投入、可见成功标准和潜在风险；用户确认后，Host 才物化既有 Project/Checkpoint/LearningTask。
5. 学习者像开始一段实习一样接收初始简报，在文件、工单、消息、指标或数据中调查和工作；Tutor 先问决策依据，再按需支架。
6. 每阶段提交真实产物。Host 按交付类型运行可确定的隐藏验证、核对 rubric 证据，并在需要时进入人工评审，再决定通过、退回修订、
   补充信息或进入下一事件。
7. 结束时先由学习者复盘目标、判断、证据与替代方案，再显示与参考工作过程的差异；正式 Attempt 和迁移验证进入证据链。
8. 有价值的改进想法可以提升为项目扩展提案，但不会反向篡改原案例版本。

### 6.5 当前插件能力与缺口

**当前：**`frontend/plugins/learning_task_conversion/` 已实现“单个真实工作任务 → 未确认候选 → 用户确认 → 一个正式
LearningTask”。候选可以包含工作情境、步骤、交付物、成功标准、知识/技能映射、rubric 和来源警告；确认后详细步骤保存到
`LearningTask.plan.work_steps`。`frontend/plugins/role_capability_graph/` 可以只读呈现岗位任务、场景、事理过程、交付物与证据边界。

  Work Case Package。
- 转换结果是一个 LearningTask，不会形成 `LearningProjectProposal`、Roadmap 或完整案例状态机。
- Web Tutor 已加载 TypeScript 插件运行层；Desktop 正式 Agent 直接调用后端 Session turn，目前没有接入同一插件执行层。

相关事实见 `docs/implementation/LEARNING_TASK_CONVERSION_XINGCHEN.md`、
`docs/implementation/PLUGIN_EXTENSION_API.md`、`frontend/server/agent-runtime.ts` 和
`backend/app/services/xingchen_learning_task_candidates.py`。

**待实现：**新增经过版本化校验的工作案例候选对象及 Host 转换入口；按案例规模输出单任务候选或
`LearningProjectProposal`。完整案例可以放在可寻址制品中，但只有 provider 提供经授权、能按精确制品/hash/selector 取回内容的
接口时，wire 才能只传地址、hash 和最小 selector；如果当前 provider 不能安全取回，就必须扩展 provider 合同以接收更大的结构化

## 7. 同一前端壳，三种默认布局

三类项目共享导航、标签、纸张、Tutor、任务控制和证据反馈，只切换默认布局与首要对象。用户可以临时移动或展开面板，但不能因
布局切换创建新的 Session 或项目状态。

```text
统一顶栏：项目 / 当前关卡 / 任务状态 / 返回锚点

左侧上下文区        中央工作区                 右侧持续 Tutor
Roadmap / 文件 /     材料纸 / 编辑器 /          当前关目标、提问、
案例对象             案例任务台                 提示和工具活动

底部：输出、正式验证、证据与恢复状态
```

| 布局 | 默认左侧 | 默认中央 | 默认底部 |
| --- | --- | --- | --- |
| 学习型 | Roadmap、来源目录、讲义与练习 | 当前材料纸和子纸 | 自检/正式练习与阅读返回点 |
| 实验型 | 本关相关文件、完整文件树、Roadmap | 多标签编辑器；纸张按对象叠入 | 构建/检查/测试输出与 diff |
| 实践型 | 案例阶段、对象、消息和交付清单 | 当前情境任务台或真实文件 | 隐藏验证反馈、rubric 和阶段状态 |

在窄屏中按“中央工作区 → Tutor → 左侧上下文 → 输出”的优先级折叠；任何模式都不能同时出现两个竞争主输入框。

## 8. Host、插件与外部生产系统的职责

| 责任方 | 负责 | 不负责 |
| --- | --- | --- |
| LearnFlow Host | 身份与项目 scope、来源/案例校验、插件激活、确认、Project/Roadmap/Task 物化、纸张与本地文件桥、工具授权、正式评价、事件与五核 | 不把插件候选直接当正式项目；不让模型绕过确认、判题或文件边界 |
| LearnFlow 插件 | 领域 Tool/Skill/Object/Renderer、候选案例编排、固定外部对象引用、覆盖与警告呈现 | 不直接写核心项目、LearningTask、EvidenceEvent、KernelState；不批准自己的候选 |
| Role Atlas / Hub 等来源系统 | 生产、校验、审核、版本化并发布岗位包或工作案例；保留来源与真实性 | 不替 LearnFlow 判断学生掌握；不直接操作 LearnFlow 项目或本地目录 |
| Tutor / Learning Design | 理解目标、解释候选、提出路线和教学内容、在当前可见信息内支架 | 不决定评分、阶段硬门、长期掌握或隐藏信息解锁 |
| Practice 与确定性 runtime | 提交校验、rubric、阶段转换、Attempt、纠错与迁移门 | 不根据生成文本或“看起来完成”升级证据 |

插件 API 继续使用 `tool / skill / object / tool_renderer` 四类扩展。工作案例的持久化与正式转换属于 Host 明确登记的核心接口，不能
通过扩大 Plugin Object 语义偷偷获得写权限。

## 9. 模型与确定性代码的分工

### 模型适合做

- 从学习者表达中提取项目目标、约束和待确认歧义；
- 从经过裁剪且可见的来源提出 Roadmap、工作步骤或案例候选；
- 生成讲解、同构示范、苏格拉底问题、提示和复盘措辞；
- 建议哪些文件、材料或案例对象与当前问题相关；
- 比较学习者方案，指出可核对的风险或遗漏；
- 把工具输出翻译为学生能理解的反馈。

### 必须由确定性代码或受控工具做

- learner/project/checkpoint/session ownership 与 scope 校验；
- 路径规范化、符号链接边界、文件 hash、diff、写回、回滚和幂等；
- 来源版本、案例版本、对象 hash、provenance 与可见层校验；
- Roadmap DAG、一个 Checkpoint 一个 LearningTask、阶段进入/完成与信息解锁；
- 可执行工具 allow-list、参数、环境边界、超时、输出截断和审计；
- 答案隔离、评分、rubric、通过条件、辅助等级、迁移与复习安排；
- `EvidenceEvent -> reducer -> KernelMutation -> KernelState` 的唯一写入链。

模型生成的计划、代码、案例、反馈和总结都是候选内容。工具运行、编译成功和测试结果是可审计事实，但只有登记过的评估合同能把
它们转成学习证据。

## 11. 实施顺序

### 第一阶段：统一项目简报与布局合同

2. 定义三种布局和共同的 `WorkspaceContext`：当前关、Task、文件/来源/案例引用、纸张、可用工具、验证状态。

4. 用一个 SAT 关卡验证“示范 → 陪做 → 独立验证”，再扩展整个 Roadmap。

### 第三阶段：资料项目体验补齐

1. 建立章节/页面/段落锚点和来源版本漂移提示。
2. 统一材料纸、练习纸、错题纸与返回位置。
3. 验证长课程刷新、跨设备和多 Session 恢复。

### 第四阶段：工作案例合同与离线黄金案例

1. 版本化 Work Case Package，并实现三层信息可见性 validator。
2. 增加案例候选 → 单 LearningTask 或 `LearningProjectProposal` 的 Host 提案接口。
3. 先用仓内固定、经人工核验的离线案例验收角色、阶段、事件、交付物、隐藏测试和复盘。

### 第五阶段：插件与来源生态

2. 把岗位任务、场景和工作区证据组装成待确认案例候选。

## 12. 三个黄金用户验收情境

### 12.1 课程黄金情境：从一本课程资料持续学到可迁移

**情境：**学生导入一本有稳定目录的计算机课程资料，目标是理解一个主题并完成代码/概念练习。

**验收标准：**

- 可以确认来源版本、目录覆盖和缺口，再生成可审阅 Roadmap；系统不因导入资料宣称学生掌握。
- 进入关卡后恢复到精确阅读锚点；对原文开纸追问不会复制正文或污染兄弟分支。
- Tutor 先给一个阅读目标和一个问题；需要时在同构例子上示范，不直接给正式练习答案。
- 学生完成正式练习后产生唯一 Attempt；有提示成功、独立成功和迁移成功在 UI 与事件中明确区分。
- 关闭并重开项目后，原 Session、关卡、纸张、材料版本与未完成 Task 均可恢复。

### 12.2 SAT 黄金情境：在本地 C 工程中完成一个可验收关卡

**情境：**学生把可信的 SAT/C 工程目录关联到 LearnFlow，在一个关卡中实现单子句传播或同级功能。

**验收标准：**

- 文件树读取真实目录，本关相关文件和全部文件可切换；外部 IDE 改动后 LearnFlow 能检测并安全重载。
- 学生可以选中代码开纸询问，Tutor 知道关卡、文件、行号和版本，只给当前所需支架。
- 手动保存使用版本检查；Agent 改动先给 diff，用户确认后写回，基础 hash 变化时拒绝覆盖。
- C 语法检查、构建与预设测试运行真实项目并保存真实输出；输出可附到纸张让 Tutor 解释。
- “文件存在、保存成功、编译通过、测试通过、关卡完成、掌握”在数据和界面中始终是不同状态。
- 正式独立验证通过后才产生 Practice/Knowledge 证据；删除 LearnFlow 项目不删除本地 C 工程。

### 12.3 工作案例黄金情境：完成一份经核验的软件工作案例

**情境：**学生选择一份有来源与真实性等级的公开软件工作案例，担任指定角色，在初始仓库和工单约束下调查、修改、验证并提交
交付物。

**验收标准：**

- 进入前可查看案例版本、来源、审阅状态、脱敏边界、角色、预计投入、工具范围和可见成功标准。
- 确认后物化既有 Project/Roadmap/Checkpoint/LearningTask；不会创建插件私有项目或第二套 Task 状态。
- 初始只显示角色在第一阶段应知的信息；未来事件、参考解和隐藏测试不会进入 Tutor 上下文。
- 每次提交触发确定性评价并决定修订或阶段解锁；刷新和恢复不能越过信息门。
- Tutor 的示范、提示和直接帮助被记录为辅助，最终独立验证使用未泄漏的条件。
- 结束时能追溯目标、操作、版本化交付物、工具结果、评价、帮助等级和来源，且只有正式 Attempt 进入证据链。
- 若案例来自 Role Atlas/Hub，LearnFlow 能验证完整案例制品与 selector，而不是只收到 task label/summary 或把静态导入冒充在线连接器。

## 13. 跨类型完成定义

三类项目只有同时满足以下条件才达到可发布质量：

- 项目、关卡、Task、Session、文件、纸张和证据之间有稳定可恢复的引用。
- Web 与 Desktop 对同一核心对象、确认门、评分和事件语义一致；能力不可用时明确显示，不伪装成功。
- 普通文件、受管学习对象、插件对象和学习者状态各有唯一权威，没有影子副本。
- 模型看不到 evaluator-only 内容，不能决定写文件、阶段跳转、评分、掌握或长期记忆。
- 所有外部来源、工作案例与工具运行都有 provenance、版本、覆盖和失败语义。
- 离线固定数据可以完成三条黄金流程的核心验收；在线模型和连接器只增强内容与来源，不成为核心闭环的单点依赖。
